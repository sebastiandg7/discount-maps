# Recipes: recurring owner requests

Each recipe maps a plain-language request to the files, steps, checks and docs involved. Agents: find the closest recipe, follow it, and add a new row when a request repeats. Risk tiers come from [agent-protocol.md § 2](agent-protocol.md). Trigger phrases are what the owner is likely to say (Spanish first).

## Operations on real data (red unless noted)

| Request                                                 | Where / how                                                                                                                                                                                                                                                                | Notes                                                                                                                     |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| "Hazme administrador a X" (yellow)                      | Find the id: `select id, email from auth.users where email = '…'`; then `update public.profiles set role = 'admin' where id = '<id>'` (`db query … --linked --project-ref …`). The JWT picks it up on the next sign-in                                                     | Show the email and id before running; never promote from sign-up metadata                                                 |
| "Aprueba / rechaza el negocio X" (yellow)               | Preferred: the admin does it on `/admin` (business-web). By SQL only if asked: `update public.businesses set verification_status = 'verified', verified_at = now(), verified_by = '<admin id>' where id = '<id>'` (privileged SQL bypasses the owner trigger)              | Read the row first; a rejected business shows `/pendiente` copy                                                           |
| "Borra el usuario X / la cuenta de prueba"              | `delete from auth.users where id = '<id>'` cascades to profile, business, coupons, subscription, redemptions                                                                                                                                                               | Red: list what will disappear (counts by table) and wait for "yes". QA fixtures are listed in [database.md](database.md)  |
| "Cancela / reactiva la suscripción de X"                | Preferred: the consumer does it on `/cuenta`. By SQL: apply the same patches as `cancelSubscription` / `applyNewPaymentSource` (see `packages/domain/src/lib/billing.ts`)                                                                                                  | Red when it changes access or charges; show the row before and after                                                      |
| "¿Por qué no le cobró a X?"                             | Read-only: `select * from public.subscriptions where consumer_id = …`, `select * from public.payments where subscription_id = … order by created_at desc`, then `select * from cron.job_run_details order by start_time desc limit 5`; Wompi dashboard for the transaction | Explain in plain words (trial not over, attempts exhausted, card source missing, cron secrets missing). Green: no changes |
| "Reembolsa a X"                                         | Not automated. Wompi dashboard → transaction → refund; then set the payment row `status = 'voided'` and, if access should end, cancel the subscription                                                                                                                     | Red; the owner does the refund in Wompi themselves                                                                        |
| "Cambia una clave / secreto (Wompi, Maps, VAPID, cron)" | Owner pastes the new value into the right `.env.local`, then `node scripts/vercel-env-sync.mjs --people-url … --business-url …` (or edits it in the Vercel dashboard) and redeploys; Vault secrets via the SQL editor (`supabase/README.md`, `deploy.md § 3`)              | Agent never sees values; it only confirms the feature works afterwards                                                    |
| "Publica / despliega los cambios" (yellow)              | Merged `main` auto-deploys once the GitHub repo is connected to both Vercel projects; otherwise `cd apps/<app>; pnpm exec vercel deploy --prod --yes` per app, then the smoke test in `deploy.md § 5`                                                                      | Never deploy an unmerged branch to production; previews are fine                                                          |
| "Limpia los datos de prueba antes de lanzar"            | Delete every `@discountmaps.test` user (cascade), their redemptions, and any leftover `push_subscriptions`; keep Vault `qr_token_secret`                                                                                                                                   | Red: show the list of emails and counts, wait for "yes", then run and re-check `0` rows                                   |

## Growth requests (plan first)

"Agrega un mapa de calor", "cupones por tiempo limitado con contador", "reseñas", "chat con el negocio", "varios administradores por negocio": these are new features, not recipes. Write a short plan (what changes for consumers/merchants, data model, rules that move, risks), get a yes, then implement as a new phase in `mvp-plan.md` with its own checklist and verification.
