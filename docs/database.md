# Database: Supabase workflow, conventions, gotchas

The database is the Supabase cloud project `rurjvcrmgtrznezvwkih` (linked with the CLI). There is no local stack on the dev machine (no Docker). Schema reference (full DDL, policies, RPCs) is in [mvp-plan.md § 3](mvp-plan.md); this doc is about _how to work with it_.

## Everyday commands

```sh
pnpm supabase db push --yes                                   # apply new migrations to the linked project
pnpm supabase gen types typescript --linked > /tmp/t.ts        # then prepend the "Generated by" comment
node scripts/pgtap-remote.mjs                                  # run every supabase/tests/*.test.sql on the cloud
node scripts/pgtap-remote.mjs supabase/tests/0004_x.test.sql   # one file
pnpm supabase db query "select ..." --linked --output-format json
pnpm supabase db query --file some.sql --linked
pnpm supabase db advisors --linked --output-format json        # security/perf linter
```

Regenerate `packages/supabase/src/database.types.ts` after every schema change (the file header says how). Generated **view** columns are all nullable; type props accordingly.

`db query` runs the whole file as one implicit transaction and returns only the **last row-returning statement**. The pgTAP runner rewrites assertions into a temp table to get every TAP line back.

## Migrations

Files: `supabase/migrations/<timestamp>_<name>.sql`, forward-only (never edit an applied one; add a new file). Applied so far:

| File                                             | Purpose                                                                                                                                                  |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0001_init`                                      | Enums, tables, triggers, view `businesses_public`, RPCs `nearby_businesses`, `issue_coupon_token`, `verify_coupon_token`, RLS, storage buckets           |
| `0002_grants`                                    | Explicit table/function grants; `anon` gets nothing; default privileges for future objects                                                               |
| `0003_hardening`                                 | Pinned `search_path`, PUBLIC execute revoked, policies rewritten with `(select auth.uid())`, one SELECT policy per table, write-only owner policies      |
| `0004_branches`                                  | `add_branch(...)` RPC (builds the PostGIS point), `branches_with_coords` view                                                                            |
| `0005_privileged_bypass` + `0006_privileged_fix` | `is_privileged()`; admin-only triggers let direct SQL and service_role through                                                                           |
| `0007_billing_cron`                              | `pg_cron` job `billing-run-hourly` → `net.http_post` to `<people_web_url>/api/billing/run` with `x-billing-secret`; no-op until both Vault secrets exist |

Conventions every new migration must follow:

- `security definer` functions: `set search_path = ''` and fully qualify every name (`public.`, `auth.`, `extensions.`, `vault.`). PostGIS, pgcrypto and pg_net live in `extensions`. Operators need `operator(extensions.<->)`.
- Grant explicitly: `grant execute ... to authenticated, service_role` and `revoke ... from public, anon` for every function; tables get `select/insert/update/delete` for `authenticated` (RLS filters rows) and `all` for `service_role`. The cloud project did **not** apply Supabase's default data grants.
- Policies: use `(select auth.uid())`, never bare `auth.uid()`; one permissive SELECT policy per table; split owner write access into insert/update/delete policies.
- Cross-row invariants are triggers, not CHECK constraints (e.g. `coupons_min_active`).
- Admin-only gates call `public.is_privileged()`: true when the request has no JWT claims (dashboard SQL, migrations), a `service_role` JWT, or `public.is_admin()`. **Never use `current_user` inside a definer function** (it is the owner, always `postgres`).
- The user's role is mirrored into `auth.users.raw_app_meta_data.role` by triggers (`handle_new_user`, `sync_role_to_auth`) so the JWT carries it. Promote admins with `update public.profiles set role='admin' where id='<uuid>'`; never through sign-up metadata.
- Run `db advisors` after a migration; the accepted residual warnings are the role helpers and QR functions being callable by `authenticated`, plus Supabase's own `rls_auto_enable`.

## pgTAP tests

`supabase/tests/NNNN_name.test.sql`, wrapped in `begin; select plan(N); ... select * from finish(); rollback;`.

- Create users by inserting into `auth.users` with the `pg_temp.create_user(id, email, role)` helper copied at the top of each file (the trigger creates the profile).
- Impersonate: `set local role authenticated; set local request.jwt.claims = '{"sub":"<uuid>","role":"authenticated"}';`
- Back to privileged: `reset role; set local request.jwt.claims to default;` (claims persist across `reset role`, so clear them or admin gates stay enforced).
- Expect RLS write violations with `throws_ok($$...$$, '42501', null, 'msg')`, trigger errors with `throws_ok($$...$$, 'P0001', 'MIN_ACTIVE_COUPONS', 'msg')`.
- **Scope every count to rows the test created** (`where id in (...)`): suites run against the shared cloud project, which holds QA fixtures. Start each file with `create extension if not exists pgtap with schema extensions;` so CI's fresh local stack has it.
- Suites: `0001` profiles/roles, `0002` business verification, `0003` branches, `0004` coupons minimum, `0005` nearby businesses (view + RPC: radius, category, sort), `0006` QR tokens (issue/verify, replay, tamper, expiry, lapsed coupon/subscription). Add one per feature.
- Values a later assertion needs (e.g. an issued token) go into a temp table created while privileged with `grant all on <t> to public`, so impersonated roles can read and write it. `now()` is frozen inside the transaction: forge expired tokens by computing the HMAC with the Vault secret instead of waiting.
- From an unlinked git worktree run the runner with `SUPABASE_PROJECT_REF=<ref>` (it appends `--project-ref`).

## Secrets in Vault

Postgres functions read secrets from `vault.decrypted_secrets` by name: `qr_token_secret` (exists on the cloud project), `people_web_url`, `billing_cron_secret`, `push_dispatch_secret` (still missing: they need the public people-web URL). `supabase/seed.sql` creates local values; on the cloud project create them once in the SQL editor (see `supabase/README.md`). `billing_cron_secret` / `push_dispatch_secret` must equal the people-web env values. Check what the cron job is doing with `select * from cron.job_run_details order by start_time desc limit 5`.

## Gotchas

- `getClaims()` verifies JWTs locally, so a deleted user's token stays "valid" until it expires (~1 h). Clear the `sb-*` cookie when switching fixtures.
- Cookies are per host, not per port: `localhost:3000` and `localhost:3001` share the session in dev. Logging in on one app logs you into the other (and triggers the role bounce).
- `supabase db push` runs as a temporary `cli_login_postgres` role; objects are still owned by `postgres`.
- PostgREST embeds through views work (`businesses ... branches_with_coords(name)`), but the embedded columns are typed nullable.
